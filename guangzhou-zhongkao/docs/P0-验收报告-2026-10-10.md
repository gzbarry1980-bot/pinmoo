## 四、老序列号用户兼容结果

**结论：兼容，且修复了一个会导致老用户被误判为未授权的缺陷。**

发现的问题：前端 `unlock/validation.js` 要求 `/api/access/session` 返回 `authenticated` + `entitled` + **`accessSource:'serial'`**；而真实 8787 返回的是 `accessSource` + `entitlement.status` + `serial{...}`，**没有**顶层 `entitled`。原 `serialClient.js` 读 `body.entitled`、`access.js` 返回 `source`，照此上线**老序列号用户会被全部误判为未授权**。已修复（改为识别 `entitlement.status==='active'`，并输出 `accessSource`）。

隔离实例完整往返（真实 8787 代码，独立 SQLite，测完即删）：
证据：`C:\Users\Administrator\r_e2e3.txt`

1. 生成序列号 `FQDZFVG6UD`（status=active, maxDevices=2）
2. 第 1 台设备兑换 → `{"ok":true,"entitled":true,"deviceCount":1,"maxDevices":2,"expiresInDays":180}`
3. 第 2 台设备兑换 → `entitled:true, deviceCount:2`
4. **第 3 台设备 → HTTP 409 `SERIAL_DEVICE_LIMIT`**（"该序列号已绑定两台设备"）→ **原「两台设备」约束继续生效** ✓
5. 直接查 8787：`{"authenticated":true,"entitled":true,"accessSource":"serial","entitlement":{...},"serial":{"deviceCount":2,"maxDevices":2,"remainingDevices":0}}`
6. **经我的服务端代理**：`{"authenticated":true,"entitled":true,"accessSource":"serial","serial":{"deviceCount":2,"maxDevices":2,"remainingDevices":0}}` —— 与前端 `validation.js` 所需字段**完全一致** ✓
7. 无 Cookie 对照：`{"authenticated":false,"entitled":false}` ✓

补充：8787 的来源校验 `assertOrigin` 只对 **POST** 生效，`/api/access/session` 是 GET，因此服务端代理无需带 Origin，链路成立。
