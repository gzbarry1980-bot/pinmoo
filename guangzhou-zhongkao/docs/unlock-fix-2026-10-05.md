# 本地序列号解锁修复

日期：2026-10-05。状态：本地已接通正式验证服务，公网未部署本轮前端修复。

## 原因

旧5174启动方式仅提供静态文件，对不存在的API返回首页HTML（HTTP 200）。解锁页解析失败后使用空对象，又仅检查HTTP状态，因此错误展示“已解锁”；实际权限查询仍失败。这不是序列号被正式验证的证据。

## 修复

- `npm run dev:zhongkao`：运行本地新版，默认5174，回环地址监听。必要的配置/健康/会话GET与序列号验证POST代理到 `https://zhongkao.pinmooconsulting.com`。
- 本地不开放序列号管理、订单或账号管理代理。POST必须来自当前本地同源网页；拒绝非回环Host。
- 仅代理序列号会话Cookie；本地HTTP桥接会移除该Cookie的Secure/Domain，保留HttpOnly、SameSite和有效期。正式服务器的Cookie配置未修改。该降级仅用于回环开发环境。
- 验证响应必须是有效JSON、`ok: true`、`entitled: true`及合法两设备计数，再查询真实服务端会话；未形成有效授权会话则不显示已解锁。
- 不关闭权限闸门、不新建本地授权数据库、不复制管理密钥、不自动激活序列号。

## 验证证据

- 5项响应校验及代理测试通过。
- 服务端权益测试1组通过，包含两设备上限及第三设备拒绝。
- 构建与20项规则/数据测试通过。
- 浏览器7项解锁检查通过，详见 `docs/qa-20261005/unlock-results.json`。正式服务只做健康查询和非法格式输入，非法格式在绑定/审计前被拒绝；未提交有效序列号，未占用真实设备名额。
- 正确激活、刷新恢复及返回志愿页的成功流程使用隔离HTTP测试夹具；不得称为已替用户验证真实序列号。

## 用户复测

1. 强制刷新 `http://localhost:5174/unlock/`。
2. 输入自己的序列号，确认已解锁与绑定计数。
3. 返回原任务，确认志愿表和评估区域不再被闸门遮挡。
4. 刷新页面，确认会话恢复。

本地站与公网的localStorage分属不同源，匿名设备ID可能不同；因此本地首次验证可能占用另一个设备名额，即使在同一台物理电脑上。绑定已满时仍会由正式服务拒绝，不会擅自清除既有绑定。

服务已在本地保持运行。重启时使用 `npm run dev:zhongkao`，不要再用不带权限桥接的静态启动命令测试序列号。
